# Диагностика неисправностей Multi-Area OSPF

Два практических сценария: от первичного симптома до восстановления связности. Для каждого случая сохранены исходные скриншоты диагностики.

## Сценарий 1. Пропал канал между R2 и R4

### Симптом

Пропала связь с `PC 10.0.10.2`.

![Проверка доступности конечного узла](https://github.com/user-attachments/assets/bf11fdbe-649e-49e6-9d28-3172a796f8c5)

### 1. Локализация участка потери пакетов

С помощью `traceroute` определяем, на каком участке прекращается прохождение трафика.

![Трассировка маршрута](https://github.com/user-attachments/assets/cb9cb5b6-0ddd-4964-9944-b566777d44a1)

### 2. Проверка OSPF-соседства

Команда `show ip ospf neighbor` показывает, что одного из ожидаемых соседей нет в таблице.

![Отсутствует OSPF-сосед](https://github.com/user-attachments/assets/eb5985ba-098b-4487-97d9-3863622c017c)

### 3. Проверка интерфейса

Проверяем интерфейс, ведущий к соседнему маршрутизатору. Он выключен административно. Включаем его командой `no shutdown` и повторно проверяем соседство.

![Включение интерфейса и восстановление соседства](https://github.com/user-attachments/assets/762948f2-a51b-483e-b9c3-4bea3b2d1189)

### 4. Контрольная проверка

После восстановления OSPF-соседства повторяем проверку доступности `PC 10.0.10.2`.

![Связность восстановлена](https://github.com/user-attachments/assets/83c40b42-d99f-4f6c-ac55-443715ee591a)

**Причина:** интерфейс в сторону OSPF-соседа был выключен.  
**Решение:** включить интерфейс и убедиться в восстановлении соседства.  
**Итог:** маршрутная информация и связность конечных узлов восстановлены.

## Сценарий 2. Нет OSPF-соседства между R2 и R4

### Симптом

С маршрутизатора R2 недоступен `PC 10.0.20.3`.

![Недоступность PC 10.0.20.3](https://github.com/user-attachments/assets/77b8a991-719d-4856-9194-1be6ff79f793)

### 1. Проверка соседства

В таблице OSPF-соседей R2 отсутствует R4.

![Отсутствует соседство R2–R4](https://github.com/user-attachments/assets/8630e8c6-217e-44f3-9dad-1b77aac226fa)

### 2. Проверка OSPF-конфигурации

Проверяем настройки R4. В выводе видно отсутствие необходимой OSPF-конфигурации для соответствующей области. Добавляем её и повторно проверяем состояние соседства.

![Восстановление OSPF-конфигурации](https://github.com/user-attachments/assets/a22d560e-6bbd-4733-b330-8c592ab8c411)

**Причина:** на R4 отсутствовала необходимая конфигурация OSPF для соответствующей области.  
**Решение:** добавить конфигурацию и проверить параметры смежных интерфейсов.  
**Итог:** OSPF-соседство восстановлено.

## Универсальный алгоритм диагностики

1. Проверить доступность и локализовать участок потери с помощью `ping` и `traceroute`.
2. Проверить физическое и протокольное состояние интерфейсов: `show ip interface brief`.
3. Убедиться, что интерфейсы включены в OSPF: `show ip ospf interface brief`.
4. Проверить соседство: `show ip ospf neighbor`.
5. Сверить области и другие параметры соседних устройств.
6. Проверить маршруты и LSDB: `show ip route ospf`, `show ip ospf database`.
7. После исправления повторить первоначальную проверку связности.
